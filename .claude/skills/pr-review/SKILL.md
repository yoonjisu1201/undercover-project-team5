# PR 코드 리뷰

Undercover 프로젝트의 열린 GitHub PR을 불러와 코드를 리뷰하고, 고칠 점을 한글로 정리해서 채팅에 보고한다.

**중요: 이 스킬은 읽기 전용이다. GitHub에 댓글·리뷰·라벨 등 어떤 것도 쓰지 않는다. 결과는 오직 채팅에만 정리한다.**

## 1. 리뷰 대상 PR 정하기

인자(`$ARGUMENTS`)에 PR 번호가 있으면 그 PR로 바로 진행한다. 없으면 열린 PR 목록을 보여주고 고르게 한다.

```bash
gh pr list --state open --limit 30 \
  --json number,title,author,headRefName,isDraft,updatedAt \
  --template '{{range .}}#{{.number}}  {{.title}}  ({{.author.login}}, {{.headRefName}}){{if .isDraft}} [draft]{{end}}{{"\n"}}{{end}}'
```

- 열린 PR이 없으면 그 사실을 알리고 멈춘다.
- 목록을 표로 보여주고 "몇 번 PR을 리뷰할까요?"라고 묻는다. 사용자가 번호를 고르면 그 PR로 진행한다.
- 인자로 번호를 이미 받았다면 이 질문을 건너뛴다.

## 2. PR 정보와 변경 코드 불러오기

선택한 PR 번호를 `<N>`이라 할 때:

```bash
# PR 메타 정보 (제목, 본문, 브랜치, 연결된 이슈 등)
gh pr view <N> --json number,title,body,author,headRefName,baseRefName,files,additions,deletions

# 실제 변경 diff — 리뷰의 핵심 입력
gh pr diff <N>
```

diff가 크면(수백 줄 이상) 변경 파일 목록을 먼저 파악하고, 파일 단위로 나눠서 검토한다. 필요하면 `gh pr diff <N> -- <파일경로>`로 특정 파일만 볼 수 있다.

diff만으로 맥락이 부족한 부분(호출부, 관련 정의)은 리포지토리의 실제 파일을 Read로 열어 확인한다. 지금 체크아웃된 브랜치가 PR 브랜치가 아닐 수 있으므로, 파일 내용이 diff와 어긋나면 그 diff의 "after" 코드를 기준으로 판단한다.

## 3. 리뷰 관점

변경된(추가/수정된) 코드에 집중한다. 아래 관점으로 검토한다:

1. **버그·정확성** — 로직 오류, 널 참조(`NullReferenceException`), 경계 조건, 경쟁 상태, 잘못된 상태 전이, 예외 미처리 등 실제 동작을 깨뜨릴 수 있는 문제. **가장 우선순위가 높다.**
2. **단순화** — 과한 추상화, 불필요한 유연성/설정, 불가능한 시나리오에 대한 방어 코드. 더 적은 코드로 같은 일을 할 수 있으면 제안한다. (프로젝트 CLAUDE.md의 Simplicity First / Surgical Changes 원칙)
3. **중복** — 반복되는 로직, 이미 존재하는 유틸/메서드로 대체 가능한 코드.
4. **좋은 코드 패턴** — 명명, 응집도, 기존 코드 스타일과의 일관성. Unity/C# 관례(생명주기 오용, `Update`에서의 비싼 호출, `GetComponent` 반복 호출, 직렬화 필드 처리, 네트워크 동기화 등)도 짚는다.

각 지적은 **추측이 아니라 근거를 들어** 설명한다. 확신이 낮으면 "확인 필요"로 표시한다. 스타일 취향 수준의 사소한 지적은 최소화하고, 정말 고칠 가치가 있는 것에 집중한다.

## 4. 결과 정리 (채팅에만)

다음 형식으로 한글로 보고한다:

```
## PR #<N> 리뷰: <제목>

**요약**: (변경 내용 2~3줄 + 전체 인상)

### 🔴 중요 (버그/정확성)
- `파일:줄` — 문제 설명. 왜 문제인지 + 제안.

### 🟡 개선 (단순화/중복)
- `파일:줄` — ...

### 🟢 참고 (사소함/취향)
- `파일:줄` — ...

**결론**: (머지해도 될지 / 고친 뒤가 좋은지 한 줄)
```

- 해당 심각도에 지적할 게 없으면 그 섹션은 생략한다.
- 지적이 하나도 없으면 그대로 "특별히 고칠 점 없음"이라고 정직하게 보고한다. 억지로 만들지 않는다.
- 파일·줄 참조는 `Assets/Scripts/...:42`처럼 클릭 가능한 형식으로 쓴다.

## 하지 말 것

- GitHub에 댓글/리뷰/승인/라벨 등을 남기지 않는다. (`gh pr comment`, `gh pr review` 등 쓰기 명령 금지)
- 코드를 자동으로 고치지 않는다. 이 스킬은 리뷰(지적)까지만 한다. 사용자가 고쳐달라고 하면 그때 별도로 진행한다.
- PR 범위 밖의 코드를 리뷰하지 않는다.
